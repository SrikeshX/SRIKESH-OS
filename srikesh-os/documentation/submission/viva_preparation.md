### Q1. What happens immediately after the kernel starts?
**Answer:** When the bootloader completes stage 4 loading (BIOS) or executes `ExitBootServices` (UEFI), it sets up initial 4-level page tables, initializes the GOP/VGA framebuffer, and jumps directly to `kernel_main` at virtual address `0x80000...`. Immediately, the kernel:
1. Samples the CPU Time Stamp Counter via `_rdtsc()` to start hardware boot latency telemetry.
2. Initializes the 16550A UART serial controller on port `0x3F8` (COM1) for diagnostics.
3. Disables CPU interrupts (`cli`), loads the Interrupt Descriptor Table (`lidt`), and remaps the master and slave 8259 PIC vectors to 32–47.
4. Programs the 8254 PIT channel 0 to generate periodic square-wave timer interrupts at 100 Hz.
5. Queries CPUID for vendor string (`GenuineIntel` / `AuthenticAMD`) and physical memory regions from `BootInfo`.
6. Arms the `StorageGuard` engine to lock internal host disks in read-only mode, tests ATA persistence at LBA 2048, and launches the graphical compositor.

### Q2. How is a task represented?
**Answer:** A task is represented in memory by a `TaskControlBlock` (TCB) structure:
```rust
pub struct TaskControlBlock {
    pub id: u64,
    pub priority: u8,
    pub status: TaskStatus,       // Ready, Running, Blocked, Terminated
    pub stack: TaskStack,         // 8 KB dedicated execution stack
    pub interrupt_rsp: usize,     // Saved stack pointer during preemption
    pub context: CpuContext,      // Callee-saved register storage
}
```
Each task maintains an independent stack and tracks its current execution state to facilitate seamless register restoration upon preemption.

### Q3. How does the scheduler select the next task?
**Answer:** The scheduler queries the circular FIFO `ReadyQueue`. It inspects the head of the queue via `scheduler::dispatch_next(queue)`:
1. It dequeues the task pointer from the head of the ring buffer.
2. It validates that the task pointer is non-null and currently in the `Ready` state.
3. It transitions the task's state from `Ready` to `Running`.
4. It sets the atomic global `CURRENT_TASK` pointer to this TCB and returns the task's saved stack pointer (`interrupt_rsp`).

### Q4. Why did you choose Round Robin?
**Answer:** Round Robin was selected because:
1. **Fairness & Predictability:** Every runnable task receives an equal time slice, preventing CPU starvation.
2. **Determinism:** The FIFO queue order guarantees reproducible scheduling sequences, which is essential for academic evaluation and verification.
3. **Simplicity & Low Overhead:** Selecting the next task is an $O(1)$ constant-time queue dequeue operation, minimizing interrupt latency.

### Q5. What triggers a scheduling decision?
**Answer:** A scheduling decision is triggered by hardware timer interrupts generated by the 8254 Programmable Interval Timer (PIT) at IRQ 0 (Interrupt Vector 32). Each timer interrupt invokes `timer_schedule(frame)`, incrementing the elapsed tick counter. When the elapsed ticks reach the configured time quantum (5 ticks = 50 ms), a preemptive context switch is triggered.

### Q6. What happens during a timer tick?
**Answer:** During each timer tick (10 ms interval):
1. The CPU saves `ss`, `rsp`, `rflags`, `cs`, and `rip` onto the current task's stack.
2. The global assembly wrapper `srikesh_timer_interrupt_wrapper` pushes all general-purpose registers (`rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `rbp`, `r8`–`r15`).
3. It sends an End of Interrupt (`EOI`) signal to the master 8259 PIC (`out 0x20, 0x20`).
4. It calls `timer_schedule(frame)` in Rust. If the running task's 5-tick slice has expired, its state is set to `Ready`, it is pushed to the back of the queue, the next `Ready` task is dequeued, and its saved stack pointer is returned.
5. The wrapper updates `rsp`, pops the new task's registers, and executes `iretq` to resume execution.

### Q7. How is shared kernel data protected?
**Answer:** Shared kernel structures (such as the framebuffer, VFS, ready queue, network driver, and storage guard) are protected using `spin::Mutex`. Any kernel code accessing a shared structure must first acquire the spinlock, execute the critical section, and release the lock via RAII scope guard upon exit.

---

### Q8. Why is synchronization required?
**Answer:** Without synchronization, asynchronous interrupts (such as PIT timer ticks or PS/2 keyboard events) could preempt execution in the middle of modifying a shared data structure (e.g. updating a circular queue index or writing to the backbuffer). This would cause race conditions, torn writes, pointer corruption, and kernel panics.

### Q9. How does your allocator work?
**Answer:** SRIKESH OS uses a two-tier memory architecture:
1. **Physical Frame Allocator:** Parses `BootInfo.memory_regions` to identify usable 4 KB page frames across physical RAM.
2. **Kernel Heap Bump Allocator:** Manages a 64 KB dedicated heap aligned to 4096 bytes. When memory is requested, it aligns the current allocation pointer (`aligned = (addr + align - 1) & !(align - 1)`), checks that `aligned + size <= HEAP_SIZE`, and atomically bumps the pointer forward.

---

### Q10. What happens when allocation fails?
**Answer:** When an allocation request exceeds available heap space, or when an invalid request (such as a 0-byte allocation or non-power-of-two alignment) is submitted, `memory::allocate()` returns `None`. The calling subsystem handles the `None` gracefully (e.g. logging an allocation failure or falling back to static buffers) rather than crashing or triggering an unhandled page fault.

### Q11. Where is `unsafe` used and why?
**Answer:** `unsafe` is used in five well-defined systems boundaries:
1. **Port I/O Instructions:** Executing x86 `in` and `out` instructions for PIC, PIT, ACPI, and ATA controller ports.
2. **Interrupt Context Switching:** Global assembly wrapper `srikesh_timer_interrupt_wrapper` manipulating stack pointers and executing `iretq`.
3. **Double-Buffer Blitting:** Copying 1.44 MB from the BSS backbuffer to the physical VRAM framebuffer using `core::ptr::copy_nonoverlapping`.
4. **Memory-Mapped I/O (MMIO):** Accessing Intel e1000 NIC configuration registers at physical address `0xF0000000`.
5. **Raw TCB Pointer Manipulation:** Enqueueing raw pointers in the scheduler's `ReadyQueue`.

### Q12. What invariant does your `unsafe` code rely on?
**Answer:**
1. **Stack Alignment & Integrity:** Interrupt stacks must be 16-byte aligned before calling Rust handlers, and the stack frame must strictly match the 20-word layout expected by `iretq`.
2. **TCB Lifetime:** Permanently allocated static TCB structures (`TASK1_TCB`, `TASK2_TCB`) must never be moved or dropped while referenced by the ready queue.
3. **Framebuffer Bounds:** Target blit offsets plus width/height must never exceed `frontbuffer_len` to prevent out-of-bounds video memory writes.

### Q13. What happens if two tasks access the same resource?
**Answer:** If two tasks attempt to access a protected resource simultaneously, the first task acquires the `spin::Mutex`. The second task enters a low-power CPU pause spin-loop (`core::hint::spin_loop()`) until the first task releases the lock. Mutex ownership ensures serialized, atomic access.

### Q16. How is your Micro-OS different from Linux?
**Answer:**
- **Architecture:** Linux is a massive monolithic kernel (>30M lines of C) with virtual memory isolation between user/kernel space via rings 0 and 3. SRIKESH OS is a lightweight educational microkernel (~5,000 lines of Rust `no_std`) where tasks operate in long mode with dedicated stacks.
- **Scheduling:** Linux uses the Completely Fair Scheduler (CFS) based on red-black trees and virtual runtime (`vruntime`). SRIKESH OS uses a simple, deterministic Round Robin scheduler with a circular FIFO queue and a 50 ms quantum.
- **Memory:** Linux uses complex demand paging, copy-on-write, slab/slub allocators, and swap space. SRIKESH OS uses a straightforward frame allocator and bump heap allocator.

### Q20. What is the most important limitation of your current system?
**Answer:** The lack of user-space memory isolation (paging-enforced Ring 3 privilege separation). Currently, kernel tasks share physical virtual memory without separate address spaces. If a task contains a memory corruption bug, it can theoretically compromise the entire kernel. Adding per-process page directory tables and syscall trampolines is the next architectural milestone.
